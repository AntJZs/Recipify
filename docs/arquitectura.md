# Arquitectura del Sistema

## 4.3 Justificación obligatoria del stack

| Capa / decisión | Tecnología elegida | Alternativas consideradas | Justificación técnica | Riesgos o limitaciones |
| :--- | :--- | :--- | :--- | :--- |
| **Plataforma móvil** | Android nativo (Kotlin) | Flutter, React Native | El desarrollo nativo permite el acceso total a las APIs del sistema y garantiza un rendimiento óptimo. Kotlin ofrece seguridad nula (null safety) y una sintaxis concisa que reduce errores en tiempo de ejecución. | Curva de aprendizaje inicial superior a frameworks multiplataforma y necesidad de código base específico para Android. |
| **UI** | Jetpack Compose (Migración recomendada) | XML View System | Framework declarativo que simplifica la creación de interfaces dinámicas, eliminando la necesidad de archivos XML y facilitando la reutilización de componentes mediante funciones composables. | Actualmente el proyecto utiliza ViewBinding; la migración completa a Compose requiere un cambio de paradigma y refactorización de la capa de presentación. |
| **Estado** | ViewModel + StateFlow | LiveData, RxJava | StateFlow proporciona un flujo de estado reactivo y robusto que se integra perfectamente con las Corrutinas de Kotlin. Los ViewModels aseguran la persistencia del estado ante cambios de configuración. | La gestión de flujos complejos puede incrementar la dificultad de depuración si no se implementa una arquitectura clara y unidireccional (UDF). |
| **Persistencia local** | Room | SQLite puro, Realm | Abstracción sobre SQLite que proporciona validación de consultas en tiempo de compilación y una integración fluida con flujos reactivos, garantizando la integridad de los datos locales. | Introduce una ligera sobrecarga de procesamiento debido a la generación de código y requiere migraciones manuales en cambios de esquema. |
| **Persistencia remota** | Firebase Firestore / Retrofit | Supabase, Ktor | Firestore ofrece sincronización en tiempo real y persistencia offline nativa. Retrofit se utiliza para el consumo eficiente de APIs REST externas con tipado fuerte. | Dependencia de servicios de terceros (Firebase) y posibles costos escalables según el volumen de transferencia de datos y operaciones. |
| **Autenticación** | Firebase Auth | Auth0, Custom API | Proporciona una solución integral y segura que soporta múltiples proveedores (Email, Google) con mínimos esfuerzos de implementación y alta confiabilidad. | Limitada personalización de ciertos flujos internos de seguridad y dependencia directa del ecosistema de Google. |
| **Reporte de fallos** | Firebase Crashlytics | Sentry, Bugsnag | Herramienta líder en la industria para el monitoreo de errores en tiempo real, proporcionando trazas detalladas que facilitan la identificación y resolución de bugs críticos. | Requiere la inclusión de servicios de Google Play en el dispositivo y puede impactar mínimamente el tamaño final del binario. |

La elección de este stack tecnológico se fundamenta en la búsqueda de un equilibrio entre robustez, mantenibilidad y rapidez de desarrollo. Al utilizar herramientas nativas y modernas como Kotlin y (en etapas posteriores) Jetpack Compose, se garantiza una experiencia de usuario fluida y una interfaz adaptativa. La combinación de Room y Firebase asegura que la aplicación sea resiliente a fallos de conectividad, mientras que la arquitectura basada en ViewModels y StateFlow facilita la escalabilidad del proyecto, permitiendo que nuevos desarrolladores se integren fácilmente gracias al cumplimiento de los estándares actuales de la industria Android.
